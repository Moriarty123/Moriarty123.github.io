## 弹窗组件
Vue 函数式弹窗调用方案

问题：以 Element Plus 为例，常见的弹窗写在父组件模板中，父组件需要维护弹窗的全部状态和方法，导致模板膨胀、逻辑耦合、复用困难。

方案：将弹窗封装为独立组件，通过 hook 函数动态实例化并挂载，父组件只负责调用，不维护状态。

API：openDialog(component, props?) 返回 Promise。第一个参数是弹窗组件，第二个参数是属性配置（可选）。Promise resolve 时拿到弹窗提交的数据，reject 时表示用户取消。调用方用 await 接收结果，不再关心弹窗内部如何处理。

Hook 内部流程：
- 调用方执行 openDialog 
- Hook 用 createApp 创建新实例 
- 将主应用的 appContext 拷贝到新实例（确保弹窗能访问 Pinia、Router、Element Plus 等全局依赖）
- 创建 div 挂载到 body 
- 渲染弹窗组件并传入 props 
- 返回 Promise 等待确认或取消 
- 关闭动画结束后卸载并清理 DOM。

弹窗组件约定：组件通过 emit 与 Hook 的 Promise 配合。emit confirm(data) 时 Promise resolve(data)，emit cancel() 时 Promise reject。弹窗内部自治，submit 方法包含表单校验和调接口的逻辑，成功后 emit confirm，失败则弹窗不关闭让用户重试。取消时设置 visible 为 false 并 emit cancel。

四个关键决策：
1. appContext 必须传递。createApp 创建的新实例与主应用完全独立，不传递的话弹窗无法访问 Pinia、Router、Element Plus、app.provide 注入的依赖。解决方式是赋值 app._context = mainApp._context。
2. props 只传配置，方法由组件自治。第三个参数只传属性配置，不传方法。submit 包含业务逻辑属于组件内部职责，调用方传入方法等于把控制权外移又回到耦合。弹窗通过 emit 返回结果，调用方通过 Promise 只关心数据。
3. 清理时机等关闭动画完成。弹窗关闭有过渡动画，在 emit close 的瞬间就卸载会截断动画。应监听 ElDialog 的 closed 事件而非 close 事件，动画结束后再执行 unmount 和 removeChild。
4. 挂载目标默认 body。挂到组件 DOM 内反而受其 CSS 影响，ElDialog 自带 append-to-body 效果一致，默认 body 即可，特殊场景再扩展。
优势：弹窗组件内部自治，父组件模板无弹窗代码，同一弹窗随处调用，await 调用

## 表格组件
表格组件封装方案

一、表格组件

表头通过 columns 数组配置，数据通过 props 传入。列渲染分三级：

纯文本：只配 prop + label，直接展示，统一处理空值

formatter：配 formatter 函数做简单转换（日期、金额、枚举映射）

slot：配 slot 字段走自定义插槽，用于状态标签等复杂渲染
操作列作为独立命名插槽 #operations，不放进 columns 数组。

二、查询状态管理

分页/排序/筛选/搜索拆为独立组件（SearchBar / FilterPanel / TableWrapper / Pagination），查询状态由 composable 统一管理，组件只负责渲染和触发事件。

composable 维护 queryParams、tableData、loading、error、total

提供 search/filter/sort/page 等方法，自动处理：
- 筛选或搜索变化时重置分页到第 1 页
- 搜索防抖
- 取消上一个未完成的请求，避免竞态
- 请求失败设置 error 状态

三、服务端查询

每次状态变化重新请求接口。可选将查询参数同步到 URL，支持刷新不丢状态、链接分享、浏览器前进后退。

## 创建和编辑弹窗的合并

一、方案描述

合并弹窗通过「是否传入初始表单数据」来区分两种模式：

创建模式：入口不传表单数据 → 表单为空 → 提交时走 POST，不传 ID

编辑模式：入口传入表单数据 → 预填回显 → 提交时走 PUT，必须传 ID

二、结论：合理，是业界主流做法

1. 模式区分无歧义。 入口的数据特征（有没有初始数据）天然决定了模式，模式又决定了提交行为，整条链路自洽，不需要额外标记。
2. 符合 RESTful 语义。 POST 创建新资源不需要 ID，PUT 更新已有资源必须带 ID，与 HTTP 方法语义一致。
3. 复用收益大。 创建和编辑的表单字段、布局、校验规则 90% 以上重叠，合并后只维护一份代码，改字段只需改一处，UI 一致性也有保障。

三、落地时需注意的边界情况

- 字段行为差异：部分字段创建时可编辑、编辑时只读（如用户名），或反过来编辑时才出现（如修改原因）。需要根据模式做条件渲染。
- 校验规则可能不同：创建时可能要求「用户名不重复」，编辑时用户名不可改。两种模式的 rules 需要动态切换。
- ID 的暂存与传递：提交时才传 ID 意味着组件内部需要先存住。建议入口直接传一个 recordId prop，创建时为空、编辑时有值，比靠推断 initialData 有没有更明确。
- 提交成功后的处理不同：创建成功通常需要拿返回的新 ID 做跳转或刷新，编辑成功一般只需关闭弹窗刷新列表。
- 表单状态重置：弹窗关闭后必须清空表单，否则「先编辑 → 再新建」会残留旧数据。
- 用一个显式的 mode来推断模式，让意图更明确，也方便未来扩展（比如加「只读查看模式」时不用大改结构）。


## 父子组件的接口下发
### 核心原则

**默认父组件请求，子组件展示。** 除非子组件数据完全独立且需要高度复用，才让子组件自己请求。

### 两种方案对比

|  |父组件统一请求 | 子组件各自请求 |
| --- | --- | --- |
| **数据共享** | 天然支持，只请求一次 | 可能重复请求 |
| **loading 状态** | 统一管理 | 分散割裂 |
| **子组件复用性** | 高（纯展示） | 低（耦合接口） |
| **父组件复杂度** | 偏重 | 轻量 |
| **适用场景** | 共享数据、有依赖关系 | 数据完全独立 |

### 弹窗场景（创建/更新）是特例

弹窗是**自包含操作单元**，不是纯展示组件，推荐：

-   **父组件**：传入 `visible` \+ 初始数据，监听 `@success`，收到后刷新列表
-   **弹窗子组件**：管表单 + 校验 + 调创建/更新 API，成功后 `emit('success')`

编辑模式的初始数据：父组件列表已有就 props 传入，数据不全就弹窗自己 fetch 详情。

### 一句话

**props 进来，events 出去，中间逻辑自己消化。** 父组件管"给什么数据"和"成功后做什么"，子组件管"怎么拿数据"和"怎么提交"。


## 循环子组件的属性传递
父组件一个循环子组件，传递isActive比传递activeId更好
三个原因：
1.  **性能更好** — 切换激活项时，只有旧 active 和新 active 两个子组件 prop 真正变化，Vue 只重渲染它们。传 `activeId` 则所有子组件的 prop 都变了，全部重渲染。列表越长差距越大。
2.  **复用性更强** — 子组件只需一个 boolean，不关心父组件用什么数据结构选中，换场景不用改。
3.  **职责更清晰** — 父组件管"谁该激活"，子组件管"激活了长啥样"，各司其职。
**最佳实践：** 父组件内部用 `activeId` 管状态，但传给子组件时转成 `:is-active="item.id === activeId"`，子组件点击时 emit 自己的 id 回来。

## 虚拟列表的实现原理
1.  **拆子组件**：实现组件级响应式隔离，props 不变时 Vue 跳过该子组件的 patch。优化的是更新阶段，首次渲染 VNode 仍全部创建。
2.  **computed + slice 截取可见子数组**：让 `v-for` 只遍历需要渲染的那几十条，从源头减少 VNode 创建。这是减少渲染时间的关键手段。
3.  **v-memo**：依赖不变时完全跳过 diff 计算。
4.  **rAF 节流**：滚动事件中用 `requestAnimationFrame` 包裹，每帧最多触发一次更新。
5.  **Set 的定位**：适合做选中/高亮项的 O(1) 查找标记，不适合用来配合 `v-if` 控制渲染范围——因为 `v-for` 仍会遍历全部数据，VNode 创建成本没有减少。
6.  列表项组件可以实现为作用域插槽
